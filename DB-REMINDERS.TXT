CURRENT DATABASE REMINDERS (UPDATED SCHEMA)

SYSTEM RULES (DON'T BREAK THESE)
1) All apps (mobile, web, kiosk) use PHP API only.
2) Flutter/web NEVER access MySQL directly.
3) Keep data normalized; avoid duplicates.
4) Barbers are USERS in this schema (barbers.userID).
5) Appointments are unified: APPOINTMENT or WALKIN.

CORE TABLE PURPOSES
users / roles / userRoles
- Auth + role control (Customer, Admin, Receptionist)

barbers / barberProfiles
- Barbers linked to users (availability + profile data)

serviceCategories / services
- Services grouped by category

haircuts
- Main library used for AI scan results
- faceShape + imageUrl are stored here

favorites
- User favorites (haircut or barber)

appointments / appointmentServices
- Unified flow for walk‑ins and appointments
- appointmentServices handles multiple services

walkInQueue
- Queue for walk‑in appointments

scheduleTemplates
- Barber weekly schedules + slot duration

payments / transactions
- Payment records for analytics

feedback / notifications / deviceTokens / auditLogs
- Ratings, system messages, devices, audits

kioskDevices / systemConfig / referenceTables
- Kiosk registry and configurable rules

AI HAIRSTYLE SCANNER FLOW (MAIN FEATURE)
1) Mobile opens camera and captures image.
2) Upload to /api/ai_scan.php (multipart/form-data).
3) Backend analyzes face/hair and maps to haircuts.faceShape.
4) Return matching haircuts (imageUrl + description).
5) User saves favorites if they like the result.

TABLES USED BY AI SCAN
- haircuts
- favorites
- auditLogs (optional)

DATA CONSISTENCY NOTES
- All booking/payment/feedback link to appointments.
- All AI results come from haircuts library.
- No duplicated service or haircut names in other tables.
