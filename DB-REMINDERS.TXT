CURRENT DATABASE REMINDERS (FOCUS: AI HAIRSTYLE SCANNER)

SYSTEM RULES (DON'T BREAK THESE)
1) All apps (mobile, web, kiosk) use PHP API only.
2) Flutter/web NEVER access MySQL directly.
3) Keep data normalized; avoid duplicates.
4) Barbers are USERS in this schema (barbers.userID).
5) Appointments store a primary barber + services via appointmentServices.

CORE TABLE PURPOSES
users / roles / userRoles
- Auth + role control (Customer, Admin, Receptionist)

barbers
- Staff linked to users; scheduling + analytics

services
- Duration + price define time blocks and billing

haircuts / hairstyleVariants
- Haircuts = style definitions
- Variants = AI-generated images saved for reuse

favorites
- Favorites link user to either barber or haircut

appointments / appointmentServices
- Created by mobile app
- appointmentServices allows multiple services per booking
- Status is the analytics truth

scheduleTemplates
- Weekly availability

payments / transactions
- Single payment per appointment + refund tracking

feedback
- Post-appointment rating

notifications / deviceTokens / auditLogs
- Push + audit trail

AI HAIRSTYLE SCANNER FLOW (MAIN FEATURE)
1) Mobile opens camera and captures image.
2) Upload to /api/ai_scan.php (multipart/form-data).
3) Backend analyzes face/hair and finds hairstyleVariants.
4) If not found, generate and store new variants.
5) Results returned to client and reusable for future requests.

TABLES USED BY AI SCAN
- haircuts
- hairstyleVariants
- favorites (save results)
- auditLogs (optional)

DATA CONSISTENCY NOTES
- All bookings/payment/feedback link to appointments.
- All AI outputs saved in hairstyleVariants.
- No duplicated service or haircut names in other tables.
