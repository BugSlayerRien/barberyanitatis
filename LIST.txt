MASTER LIST: Major Revision Plan

1) Define scope and success criteria
	- Inventory current features (web admin, mobile app, APIs, database, uploads)
	- Decide what stays, what is replaced, and what can be deferred
	- Capture performance, uptime, and security targets

2) Audit current architecture and dependencies
	- Map API endpoints, database tables, file uploads, and background jobs
	- Identify third-party services, API keys, and environment variables
	- Check OS-specific paths and hard-coded values in code and configs

3) Choose hosting and deployment model
	- Pick target hosting (shared, VPS, managed, container platform)
	- Decide on deployment method (manual, CI/CD pipeline)
	- Define environments (dev, staging, production)

4) Prepare infrastructure and security baseline
	- Create hosting accounts, DNS, SSL certificates, and firewall rules
	- Set up secrets management and environment variable strategy
	- Plan backups for database and file uploads

5) Plan the database migration (MySQL -> PostgreSQL)
	- Review schema compatibility (data types, auto-increment, indexes, constraints)
	- Decide migration tool (pgloader, custom ETL, or SQL rewrite)
	- Create a migration plan with rollback and verification steps

6) Update backend data layer for PostgreSQL
	- Replace MySQL-specific SQL with PostgreSQL-compatible SQL
	- Update connection logic, drivers, and environment configs
	- Review stored procedures/triggers and rewrite as needed

7) Update API and application code for new DB
	- Validate queries, pagination, date/time handling, and transactions
	- Update any ORM or query builder settings
	- Retest all endpoints and critical flows

8) Migrate data and verify integrity
	- Run migration in staging first
	- Validate row counts, key relationships, and constraints
	- Compare sample data and run smoke tests

9) Update file storage and uploads strategy
	- Decide where uploads live in hosting (local vs object storage)
	- Update paths, permissions, and access policies
	- Add cleanup and retention rules

10) Prepare hosting deployment
	 - Move API code, mobile build configs, and web admin assets
	 - Configure web server (Nginx/Apache), PHP, and runtime settings
	 - Set up database connections and environment variables

11) Add monitoring and logging
	 - Configure error logging and basic health checks
	 - Add performance monitoring and alerting
	 - Ensure logs do not expose sensitive data

12) Run comprehensive QA
	 - Test admin, receptionist, and mobile flows
	 - Validate authentication, bookings, services, and notifications
	 - Confirm data consistency between UI and database

13) Plan cutover and rollback
	 - Choose maintenance window
	 - Freeze writes, migrate final delta, and switch DNS
	 - Keep rollback path ready (old DB, old hosting)

14) Post-launch hardening
	 - Review logs, fix critical bugs
	 - Optimize slow queries and add indexes
	 - Document new ops and maintenance steps


POSTGRESQL MIGRATION - CRUCIAL REMINDERS

1) Fresh start means no data migration; keep only schema.
2) Freeze schema changes during conversion to avoid drift.
3) Decide Postgres version early (impacts data types and features).
4) Replace AUTO_INCREMENT with SERIAL or IDENTITY.
5) Replace TINYINT(1) with BOOLEAN where appropriate.
6) Replace DATETIME with TIMESTAMP or TIMESTAMPTZ (be consistent).
7) ENUM must become CHECK constraint or lookup table.
8) Remove MySQL ENGINE / CHARSET / COLLATION clauses.
9) MySQL-specific SQL: IFNULL -> COALESCE; CONCAT handling; date functions.
10) Verify queries that rely on MySQL implicit GROUP BY behavior.
11) Update environment variables and DB credentials for all environments.
12) Validate schema application on a clean Postgres DB before code changes.
13) Update seed.sql (if used) to PostgreSQL syntax.
14) Run smoke tests for auth, booking, services, users, notifications.
15) Ensure backups for uploads if cutover touches file paths.



FIRST STEPS (Do These First)

A) Confirm goals and priorities
	- List the top 3 outcomes for the revision (e.g., stability, scalability, lower hosting cost)
	- Identify the non-negotiables and what can be postponed
	- Set a target timeline and release window

B) Create a system inventory
	- Collect current API endpoints, DB tables, uploads, and cron/background jobs
	- Identify all environment variables and secrets currently in use
	- Note any hard-coded paths or OS-specific assumptions

C) Decide target hosting and PostgreSQL stack
	- Choose hosting provider and plan (VPS, managed, container platform)
	- Choose PostgreSQL version and hosting option (managed vs self-hosted)
	- Decide on staging vs production setup

D) Define migration strategy
	- Pick a migration tool (pgloader, ETL, or manual SQL rewrite)
	- Decide how to handle data downtime (maintenance window vs live cutover)
	- Outline rollback plan if migration fails

E) Create a staging environment
	- Set up hosting, domain, and SSL in a staging environment
	- Deploy current API and web admin to staging
	- Prepare a staging database for migration tests
